# LG Aimers 9기 — 투구 제구 성공 확률 예측

KBO 투구 데이터로 **제구 성공 확률**을 예측하는 코드 제출형 해커톤. 이 레포는 지금까지의 실험 기록·모델 구조·검증 프로토콜을 팀원이 이어받을 수 있게 정리한 것이다.

> **먼저 읽을 것**: [`docs/PROTOCOL.md`](docs/PROTOCOL.md)
> 우리는 CV 점수를 믿었다가 리더보드에서 두 번 손해를 봤다. 실험을 돌리기 전에 검증 규칙부터 읽어야 같은 실수를 반복하지 않는다.

---

## 대회 개요

| 항목 | 내용 |
|---|---|
| 대회 | LG Aimers 9기 온라인 해커톤 (Phase 2) |
| 과제 | 투구 직전 상태로 `control_success` (제구 성공 여부) 확률 예측 |
| 지표 | **Brier Skill Score × 100000** = `max(0, 100000 × (1 − BS / (r·(1−r))))` |
| | `BS = mean((p_i − y_i)²)`, `r` = 평가 데이터 전체 제구 성공률(비공개) |
| 학습 데이터 | `train.csv` 1,475,092행 × 49컬럼 (2019–2024 시즌) |
| 보조 데이터 | `trackman_history.csv` 1,793,078행 × 30컬럼 (2019–2024) |
| 평가 데이터 | `test.csv` — **2025 시즌**, 비공개. 제출 시 서버에서 교체 |
| 제출 방식 | `model/` + `script.py` + `requirements.txt` 를 zip으로. 서버가 추론 실행 |
| 제출 제한 | 1일 5회 |

지표 감각: 점수 1000 ≈ **분산의 1%만 설명**한다. 극저신호 문제라 5점, 10점 차이가 순위를 크게 바꾼다.

## 핵심 발견 세 가지

### 1. `asof_*` 컬럼에서 투구별 숨은 라벨 7종이 복원된다

`asof_pitcher_*_rate` 는 **누적 비율**이다. `asof_pitcher_n` 을 곱해 누적 횟수로 바꾼 뒤 투수별로 정렬해 차분하면 **그 투구 하나의 결과**가 나온다. 투수 792명 전원이 `asof_pitcher_n` 0부터 빈틈없는 연속 수열이라 가능하다.

복원되는 라벨: `reverse`, `middle`, `ball`, `strike` (결과 성분 4종) + `fastball`, `breaking`, `offspeed` (구종 3종).
역산한 success 라벨과 실제 `control_success` 의 **일치율 1.000000** (147만 행).

타깃 구조도 드러났다: **`control_success = ¬reverse ∧ ¬middle ∧ Z`**

### 2. 신호는 투수 정체성에 몰려 있다

모델 없이 잰 각 컬럼군의 정보 함량 (BSS 상한, 표본 노이즈 보정):

```
투수 ID              797
투수 커리어 제구율      607
구종 (역산)           212
시즌                 147
타자 ID              121
볼카운트               31
이닝 25 · LI 22 · 주자상황 3.9
```

상황 변수는 예상보다 훨씬 약하다. 볼카운트 전체 폭이 3.9%p인데 구종 하나가 5.5%p를 만든다.
**이래서 상황 관련 피처가 계속 실패했다** (성분×상황 −11.4, 콜드스타트 −1.5).

### 3. 가장 큰 신호는 규칙상 접근 불가

| 정보 | 알면 (오라클) | 예측하면 (합법) |
|---|---|---|
| 구종 | **+182.9** | +1.8 |

구종을 알면 폴드2024 BSS가 822.8 → 1005.7 이 되지만, 투구 전 정보로 예측한 정확도는 54.94%(최빈 52.26%)에 그친다. 그리고 규칙이 "현재 투구의 실제 구종"을 명시적으로 금지한다.

**투구 후 확정되는 정보는 값어치가 크고, 투구 전 정보는 거의 소진됐다**는 게 현재 진단이다.
